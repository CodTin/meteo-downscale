## Workflow

Use the installed `linear` CLI with workspace `yu-xiao`, team `YU` (UUID `98523d41-389b-49b2-8461-f42dcb2d9976`), and project `meteo-downscale` (UUID `6f1095a4-c2b5-40d6-9074-896a64018fd8`). The repository's `.linear.toml` sets the workspace, team, and default unassigned behavior; always explicitly pass `--project 6f1095a4-c2b5-40d6-9074-896a64018fd8` when creating or querying issues because the CLI has no default-project setting.

### Creating issues

Create issues with:
```bash
linear issue create --project 6f1095a4-c2b5-40d6-9074-896a64018fd8 \
  --title "<title>" \
  --description-file <file.md> \
  --state Todo \
  --label ready-for-agent \
  --no-interactive
```

Use this for approved specs and implementation tickets; use the originating skill's body template and check for duplicates first.

### Listing issues

List project issues using:
```bash
linear issue query --project 6f1095a4-c2b5-40d6-9074-896a64018fd8 --json --limit 0
```

Optionally add `--search "<keywords>"` or `--label "<label>"`. Prefer `query` over `list`, which defaults to the current user's unstarted issues.

### Reading issues

Read issues with:
```bash
linear issue view YU-123 --json --no-download
```

Read comments with:
```bash
linear issue comment list YU-123 --json
```

Use `linear api` with paginated GraphQL queries when complete comments, author/timestamp metadata, child lists, or dependency states are needed.

### Dependencies and relationships

Create tickets before wiring their native dependencies:
- `linear issue relation add YU-124 blocked-by YU-123` means YU-123 must precede YU-124
- `linear issue relation add YU-123 blocks YU-124` expresses the same edge, so run only one

Verify with `linear issue relation list YU-124`, and inspect blocker states because completed blockers can retain their relation records.

Use `--parent YU-123` for genuine child issues; parenthood alone does not imply blocking, and splitting a spec must not close or rewrite its parent.

### Labels

All required labels now exist:
- **Category**: map `bug` to `Bug` and `enhancement` to `Feature`
- **Triage**: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`
- Keep exactly one category and one triage label on each triaged issue

Change labels with:
```bash
linear issue update YU-123 --remove-label "<old>" --add-label "<new>"
```

This preserves unrelated labels.

### Workflow states

These labels are separate from workflow states. Use exact names:
- `Backlog`
- `Todo`
- `In Progress`
- `In Review`
- `Done`
- `Canceled`

Rejected `wontfix` issues should be canceled rather than marked done.

### Wayfinder labels

For wayfinder, reuse existing labels:
- `wayfinder:map`
- `wayfinder:research`
- `wayfinder:prototype`
- `wayfinder:grilling`
- `wayfinder:task`

Maps are parent issues, and eligible work consists of open, unassigned children with resolved blockers.

### Claiming and commenting

Claim a ticket with:
```bash
linear issue update YU-123 --assignee self
```

Review canceled prerequisites before assuming their requirements were satisfied.

Post briefs or resolutions using:
```bash
linear issue comment add YU-123 --body-file <comment.md>
```

Every issue or comment published during triage must begin with:
```
> *This was generated by AI during triage.*
```

### Authentication and references

Reuse existing keyring authentication, keep credentials out of the repository, and reference work using full `YU-<number>` identifiers and Linear URLs.
